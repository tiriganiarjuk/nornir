# Building Nornir

Do NOT run `cargo build --release` or `maturin build` directly.
Use `nornir_deploy` instead.

## Why

1. **Dependency coherence.** When a shared crate changes (e.g., `datagram_io`, `schemas_embedded`), ALL consumers must rebuild together. Running `cargo build --release -p one_crate` leaves other binaries in the same category running stale code. Strange runtime bugs with no obvious cause.

2. **Deployment.** `cargo build` puts binaries in cargo's target dir — on the Derived volume, per `.cargo/config.toml`, not under this repo. They are not deployed until **copied** to `~/ai/tools/bin/` (copied, never symlinked: a deployed tool must keep working with that drive unplugged). The deploy tool handles build, copy, and verification of the deployed copy as one atomic operation.

3. **Gates require maturin.** PyO3 gate modules cannot be built with `cargo build`. They need `maturin build`, wheel extraction, and `.so` deployment to `~/ai/tools/lib/`. The deploy tool handles all of this.

4. **Schema embedding.** Schemas are embedded at compile time via `include_str!()`. A changed `.schema.json` has no effect until the consuming binary is rebuilt and redeployed.

## Approved interfaces — the only shapes a tool exposes

A tool's interface is decided once, by the author, and every tool of its kind implements it
exactly. A crate exposes only an approved interface. Building a tool whose need no approved
interface meets is a stop: say what the tool must return, and the author decides the shape
before the crate is written.

A tool whose job needs more than its kind's contract carries gets an approved extension: its
own row below, stating what it adds and *why*. The contract's frame — `ok`, `data`,
`error.type`, nothing raised — holds for every extension.

| Kind | Its interface |
|------|---------------|
| PyO3 module that reads, validates or checks — gates, readers | returns `{"ok": bool, "data": str \| None, "error": {"type": str, "message": str} \| None}` for every outcome of the read or check; `data` is the validated JSON string — for `read_tomlx_json_schema`, the object `{"data": …, "schema": …}`; for an output or passthrough gate, `None`, because the write is the effect; the defaults gate returns the data it wrote |
| PyO3 module that validates text or verifies bytes, and writes the file — text writers, binary writers | the same contract; a write hands nothing back, so `data` is always `None`. A text writer writes nothing without a schema: one that cannot be read or compiled is a `schema_error` |
| PyO3 module that makes a thing exist or not exist — the presence tools | the same contract; the effect is the existence, so `data` is always `None`. A flag already there is created and a flag already gone is removed: nothing to do is success |
| PyO3 module that replaces a generated directory whole — the directory writer | the same contract, with `data` carrying the run's accounting — `{"written": int, "unchanged": int, "removed": int}`, validated against `schemas/tools/directory-write-report.schema.json`. *Why it extends:* every run must state what it did, and a byte-identical file kept in place is indistinguishable from one rewritten unless the tool that kept it says so |
| PyO3 module that reads a binary file — binary readers | returns `{"ok": bool, "data": str \| None, "payload": bytes \| None, "error": {"type": str, "message": str} \| None}` for every outcome; `payload` is the decoded content as bytes, and `data` is the validated JSON string that describes it — its dimensions, its number format, what was found in it. The caller validates `data` into a model and reads `payload` by what the model says. On failure both are `None` |
| CLI binary | the CLI contract, below |
| hook | `hook_io`: a pure `decide` function over `HookInput`, and the response builders in `hook_io::response` |
| writer, store | `write_engine` / `store_engine`, generated by `generate_writer.py`: the CLI contract, with success carrying a receipt on stdout. A writer's receipt is `{"written": int}`, and for a writer that stamps also `"last_record_stamps"` — the stamped fields of the last record written, under the writer's own field names; with `written`, the last sequence gives the whole range. It is validated against `schemas/tools/write-receipt.schema.json`, built before the write so that a write on disk always has its receipt, and names no path. A store's receipt is the stored session's id. *Why it extends:* the caller is an agent, and a write it cannot tell from nothing happening is a write it makes again — on an append, a duplicate record nothing downstream catches; and a stamp is a value the author may not supply, so the receipt is the one place the author learns what its record was given |

### The CLI contract

A CLI binary carries the same information as the PyO3 contract — the data, the failure class and
its message — presented for a shell and for the next program in a pipe:

| Outcome | stdout | stderr | exit code |
|---|---|---|---|
| success | the validated data, exactly | — | 0 |
| refusal or failure | — | first line: the failure class (`error.type`); then the message, as plain text | 1 |
| wrong arguments | — | the usage, and its route | 2 |

### `error.type` — the failure classes

`error.type` names the failure class, taken from the engine's typed error by its
`error_type()` method: one type per class a caller can act on differently. A caller branches
on `error.type`; `error.message` is for people.

The table is generated from the error registry, `core/failure_mode_core/failure_modes.toml`:
every class, and the failure modes that carry it. Each mode's entry in the registry says what
failed and what to do next. `cargo test -p failure_mode_core` fails while this table is behind
the registry.

### Calling one from Python

The wrapper is the project's `ffi.py`; it types the result at once, so no dict travels past it.
The contract has two outcomes and no others, so each is its own model, and a result that is
neither fails validation where it arrives:

```python
from typing import Annotated, Literal

from pydantic import BaseModel, Field, RootModel

class ToolError(BaseModel, frozen=True):
    type: str
    message: str

class ToolSuccess(BaseModel, frozen=True):   # a tool that hands data back: readers, input gates
    ok: Literal[True]
    data: str
    error: None

class ToolRefusal(BaseModel, frozen=True):
    ok: Literal[False]
    data: None
    error: ToolError

class ToolResult(RootModel[Annotated[ToolSuccess | ToolRefusal, Field(discriminator="ok")]]):
    pass

outcome = ToolResult.model_validate(read_toml_validate_json.read(path, schema_name, schema_dir)).root
```

The caller matches on the outcome's type. A `ToolRefusal` carries `error.type` to branch on,
and each project decides what a class means at that call site: a hard failure, a held-back
item, a report line. A `ToolSuccess` carries `data` for `Model.model_validate_json(outcome.data)`.

For the kinds whose effect is the write — output and passthrough gates, text writers, binary
writers, presence tools — success carries no data: its model is `ok: Literal[True]`,
`data: None`, `error: None`. The Approved interfaces table above says which kind returns which.

## Commands

```
nornir_deploy --all                  # rebuild + deploy everything
nornir_deploy --non-pyo3             # all cargo crates, skip maturin gates
nornir_deploy --build hooks          # single category
nornir_deploy --build hooks,writers  # multiple categories
nornir_deploy --list                 # show categories and crate counts
```

Categories are defined in `deploy_categories.toml`.

## Adding a new crate

The steps are in `NORNIR_CONVENTIONS.md` § Adding a New Crate. `nornir_deploy` finds a crate's
directory through the workspace `Cargo.toml` members, so a crate listed in
`deploy_categories.toml` but not in the workspace cannot be built.

## What is safe to run directly

- `cargo check` — compilation checking, no deployment
- `cargo test` — run tests
- `cargo clippy` — lint checking
- `cargo build` (debug, no `--release`) — compilation checking, produces debug binaries only

A hook intercepts `cargo build --release` and `maturin build` to remind you.

## deploy_categories.toml Reference

Each table in `deploy_categories.toml` is a category. These are the fields `nornir_deploy` reads:

| Field | Meaning |
|-------|---------|
| `crates` | cargo binaries: built, copied to `~/ai/tools/bin/`, verified with `verify` |
| `verify` | how a `crates` binary is checked — a method from the table below (default `help`) |
| `verify_input` | JSON piped to stdin when `verify = "stdin"` |
| `valid_exit_codes` | accepted exit codes when `verify = "exit_codes"` |
| `binary_names` | crate name → binary name, where they differ (`saga_cli = "saga"`) |
| `cli_crates` | cargo binaries verified with `cli_verify` instead of `verify` |
| `cli_verify` | how a `cli_crates` binary is checked (default `help`) |
| `pyo3_crates` (or `gate_crates`) | PyO3 modules: built with maturin, `.so` extracted and codesigned into `~/ai/tools/lib/`, verified by `python_import` |
| `python_version` | the interpreter maturin builds for and imports with (default `python3.13`) |

| Method | What it does | When to use |
|--------|-------------|-------------|
| `help` | Runs `binary --help`, accepts exit 0 or 1 | Binaries with clap or manual `--help` |
| `stdin` | Pipes `verify_input` to stdin, expects exit 0 | Binaries that read JSON from stdin (hooks, converters, rewriters) |
| `exit_codes` | Runs the binary with no arguments, accepts any code in `valid_exit_codes` | Binaries that exit non-zero on missing arguments but prove they load |
| `python_import` | Runs `python -c "import <module>"`, expects exit 0 | Every PyO3 module |

**Two-faced crates need no entry for their CLI face.** A PyO3 crate whose `Cargo.toml` declares a
`python` feature is built by maturin with that feature on. If it also declares a `[[bin]]`, its
CLI face is built by cargo without the feature, copied to `~/ai/tools/bin/`, and verified to exit 2
with no arguments — the CLI contract's wrong-arguments outcome. Which faces a crate has is read
from its own manifest, never listed here.

**`nornir_deploy --bootstrap`** creates the `nornir_deploy` symlink in `~/ai/tools/scripts/`, which
is how it is on `PATH`.
