# Building Nornir

Do NOT run `cargo build --release` or `maturin build` directly.
Use `nornir_deploy` instead.

## Why

1. **Dependency coherence.** When a shared crate changes (e.g., `datagram_io`, `schemas_embedded`), ALL consumers must rebuild together. Running `cargo build --release -p one_crate` leaves other binaries in the same category running stale code. Strange runtime bugs with no obvious cause.

2. **Deployment.** `cargo build` puts binaries in cargo's target dir — on the Derived volume, per `.cargo/config.toml`, not under this repo. They are not deployed until **copied** to `~/ai/tools/bin/` (copied, never symlinked: a deployed tool must keep working with that drive unplugged). The deploy tool handles build, copy, and verification of the deployed copy as one atomic operation.

3. **Gates require maturin.** PyO3 gate modules cannot be built with `cargo build`. They need `maturin build`, wheel extraction, and `.so` deployment to `~/ai/tools/lib/`. The deploy tool handles all of this.

4. **Schema embedding.** Schemas are embedded at compile time via `include_str!()`. A changed `.schema.json` has no effect until the consuming binary is rebuilt and redeployed.

## Approved interfaces — the only shapes a tool exposes

A tool's interface is decided once, by the author, and every tool of its kind implements it
exactly. A crate exposes only an approved interface. Building a tool whose need no approved
interface meets is a stop: say what the tool must return, and the author decides the shape
before the crate is written.

| Kind | Its interface |
|------|---------------|
| PyO3 module that reads, validates or checks — gates, readers | returns `{"ok": bool, "data": str \| None, "error": {"type": str, "message": str} \| None}` for every outcome of the read or check; `data` is the validated JSON string — for `read_tomlx_json_schema`, the object `{"data": …, "schema": …}`; for an output or passthrough gate, `None`, because the write is the effect; the defaults gate returns the data it wrote |
| PyO3 module that validates text or verifies bytes, and writes the file — text writers, binary writers | the same contract; a write hands nothing back, so `data` is always `None`. A text writer writes nothing without a schema: one that cannot be read or compiled is a `schema_error` |
| PyO3 module that reads a binary file — binary readers | returns `{"ok": bool, "data": str \| None, "payload": bytes \| None, "error": {"type": str, "message": str} \| None}` for every outcome; `payload` is the decoded content as bytes, and `data` is the validated JSON string that describes it — its dimensions, its number format, what was found in it. The caller validates `data` into a model and reads `payload` by what the model says. On failure both are `None` |
| CLI binary | Binary Structure in `NORNIR_CONVENTIONS.md`: `Result` in helpers, exit codes 0 / 1 / 2 from `main()` only |
| hook | `hook_io`: a pure `decide` function over `HookInput`, and the response builders in `hook_io::response` |
| writer, store | `write_engine` / `store_engine`, generated by `generate_writer.py` |

### `error.type` — the failure classes

`error.type` names the failure class, taken from the engine's typed error by its
`error_type()` method: one type per class a caller can act on differently. A caller branches
on `error.type`; `error.message` is for people. A new class joins this table when an engine
first produces it.

| `error.type` | What failed | Produced by |
|---|---|---|
| `read_error` | the file could not be read | gates, readers, binary readers |
| `parse_error` | the file, or the text or bytes handed to a writer, is not valid in its own format | gates, readers, binary readers, text writers, binary writers |
| `conversion_error` | the format→JSON conversion produced invalid JSON — an engine fault | gates, readers |
| `schema_error` | the schema could not be loaded or compiled, or a tomlx file has no annotations to derive one | gates, readers, text writers |
| `validation_error` | the data does not match the schema | gates, readers, text writers |
| `cache_error` | the validator cache failed — an engine fault | readers, text writers |
| `path_error` | a path the data names does not exist | gates that verify paths |
| `verification_error` | the bytes are well formed but carry more than the stated shape, or a different one | binary readers, binary writers |
| `rules_error` | the rules the caller stated are invalid, or do not fit the data | binary readers |
| `repair_error` | a bad value has no good neighbour to repair from | binary readers |
| `compression_error` | the bytes could not be compressed | binary writers |
| `write_error` | the output could not be written | gates, text writers, binary writers |

### Calling one from Python

The wrapper is the project's `ffi.py`; it types the result at once, so no dict travels past it:

```python
class ToolError(BaseModel, frozen=True):
    type: str
    message: str

class ToolResult(BaseModel, frozen=True):
    ok: bool
    data: str | None
    error: ToolError | None

result = ToolResult.model_validate(read_toml_validate_json.read(path, schema_name, schema_dir))
```

The caller matches on `result.ok` and then on `result.error.type`, and each project decides
what a class means at that call site: a hard failure, a held-back item, a report line. On
success, `Model.model_validate_json(result.data)`.

## Commands

```
nornir_deploy --all                  # rebuild + deploy everything
nornir_deploy --non-pyo3             # all cargo crates, skip maturin gates
nornir_deploy --build hooks          # single category
nornir_deploy --build hooks,writers  # multiple categories
nornir_deploy --list                 # show categories and crate counts
```

Categories are defined in `deploy_categories.toml`.

## Adding a new crate

1. Add the crate to `deploy_categories.toml` under the appropriate category.
2. Run `nornir_deploy --build <category>`.

## What is safe to run directly

- `cargo check` — compilation checking, no deployment
- `cargo test` — run tests
- `cargo clippy` — lint checking
- `cargo build` (debug, no `--release`) — compilation checking, produces debug binaries only

A hook intercepts `cargo build --release` and `maturin build` to remind you.

## deploy_categories.toml Reference

Each category in `deploy_categories.toml` specifies a `verify` method that nornir_deploy runs after building to confirm the binary works.

| Method | What it does | When to use |
|--------|-------------|-------------|
| `help` | Runs `binary --help`, expects exit 0 | Binaries with clap or manual `--help` |
| `stdin` | Pipes `verify_input` JSON to stdin, expects exit 0 | Binaries that read JSON from stdin (hooks, converters, rewriters) |
| `exit_codes` | Runs binary with no args, accepts any code in `valid_exit_codes` | Binaries that exit non-zero on missing args but prove they load |
| `python_import` | Runs `python -c "import <module>"`, expects exit 0 | PyO3 `.so` modules (gates, interceptors) |

Additional fields:
- `verify_input` — JSON string piped to stdin (required when `verify = "stdin"`)
- `valid_exit_codes` — list of accepted exit codes (required when `verify = "exit_codes"`)
- `binary_names` — optional table mapping crate name to binary name when they differ (e.g., `saga_cli = "saga"`)
- `pyo3_crates` — crates built with maturin instead of cargo
- `python_version` — Python version for maturin builds (e.g., `"python3.13"`)
